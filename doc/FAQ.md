# 常见问题（FAQ）

[文档导航](README.md) · [首次部署](first-deployment.md) · [部署与维护](../deploy/README.md)

## Auth 登录后为什么根路径仍提示认证？

如果访问根路径 `/` 显示：

```text
dsh web authentication required; reopen the URL printed by dsh web.
```

这是官方 DSH 控制台的浏览器认证提示，不能据此判断模型 API 密钥缺失。三种凭据的用途不同：

| 凭据 | 用途 | 使用者 |
| --- | --- | --- |
| 插件 Auth 账号与会话 | 登录 `/auth`，按授权进入应用 | 管理员和普通用户 |
| 官方 DSH 控制台认证地址及 Cookie | 进入根路径 `/` 的官方控制台 | 站点维护者 |
| 模型提供方 API 密钥 | 让宿主调用模型生成回答 | 站点维护者配置，应用使用 |

只使用应用时，从 `/auth` 打开已授权应用，例如 `/example`。默认 DeepSeek 密钥可由管理员在 `/auth` 的“模型设置”管理；需要访问完整官方控制台时，在服务器仓库根的私有终端读取官方认证地址：

```sh
cat .local/data/dsh-web-auth-url.txt
```

在自己的浏览器打开文件中的完整地址，包含 `?token=...`。官方 DSH 校验后设置浏览器 Cookie，并跳转到不带令牌的 `/`。示例是默认路径；如果改过 `dataRoot` 或 `authUrlFile`，按 `.local/deployment.json` 的实际路径读取。文件不存在或为空时检查启动是否完成及日志中的“DSH 认证地址已保存至 …”，不要自行编造令牌。

认证地址具有控制台访问能力，不要发给普通用户、贴入工单或截图分享。Auth 账号权限不会自动授予官方控制台访问权。

## 官方认证地址为什么会失效？

启动令牌随官方 DSH 进程重新生成。服务重启后重新读取当前文件，不用旧书签中的 token。清理 Cookie、更换浏览器或更换域名后，也可能需要重新认证。有效的既有 Cookie 不一定随每次重启失效。

如果文件中的域名不对，检查站点的 `publicUrl`、`publicOrigin` 与实际访问地址，并按部署流程应用配置。如果完整的新地址仍返回 401，检查反向代理是否保留查询参数、正确转发 Host 和 Cookie；不要通过关闭认证解决。

## 第一次如何在服务器手动录入 DeepSeek API 密钥？

完成首次部署后，在服务器仓库根执行：

```sh
bash deploy/scripts/set-api-key.sh --config .local/deployment.json
```

在提示后粘贴密钥并按 Enter，输入不会显示；Ctrl+C 取消。脚本已随仓库提供，无需下载额外脚本或安装新的工具。需要可交互的 SSH 终端；非交互 stdin 只供受信任的密钥管理工具使用，不要把密钥放在 shell 命令中。

也可由管理员在 `/auth` →“模型设置”填写或更换。网页与脚本共用官方凭据服务，保存到当前 home 的 `.credentials.yaml`，无需重启；默认宿主自动监听脚本写入，后续请求使用新密钥。此密钥是宿主级配置，不是每个 Auth 用户单独填写，也不放入业务插件配置。脚本的运行条件见[首次登录与模型密钥](first-deployment.md#首次登录与模型密钥)。

## 页面显示的指纹能还原密钥吗？“已配置”代表有效吗？

不能。后端只返回 SHA-256 指纹，不返回原密钥；这是不可逆摘要，不是可解密的密文。宿主调用模型仍需原始凭据，因此原密钥由官方凭据存储保存在服务器，不能仅保存摘要。管理员可比较指纹判断是否更换成功；“已配置”只表示存在凭据，不代表认证、余额、网络或模型调用验证通过。

## 为什么显示外部环境只读？

官方凭据优先级为：继承的进程环境 > `.credentials.yaml` > 工作目录 `.env` > home `.env`。进程环境是外部注入的明确覆盖，两个入口都会拒绝覆盖，避免无效保存。由服务管理者移除对应环境注入并调整启动配置后，才能通过页面或脚本管理。旧 `.env` 不必删除，新存储优先于它。

## 密钥已保存，为什么问答仍然失败？

按实际错误逐项核对：

1. **核对运行状态**：在“模型设置”刷新配置状态与指纹。默认宿主无需重启；如果自定义了凭据存储路径或关闭文件监听，使用网页更新实际运行服务。
2. **写错实例**：使用与当前站点相同的 `.local/deployment.json`；CLI 参数和环境变量可覆盖实例路径，避免遗留 `DSH_HOME`、`DSH_DATA_DIR` 指向其他实例。脚本会核验活动 Compose 容器的 home 挂载。
3. **密钥被外部环境覆盖**：检查是否显示只读，以及实际模型是否使用默认 `DEEPSEEK_API_KEY` 引用。自定义提供方或凭据引用不在此页面的管理范围。
4. **模型选择不匹配**：设置 `DEEPSEEK_API_KEY` 不会选择模型，也不会配置其他提供方。通过官方控制台选择可用提供方和默认模型，操作见[模型准备](../packages/plugin-manager/DELIVERY.md#问答应用的模型准备)。
5. **密钥或服务不可用**：核对具体模型错误，包括认证失败、余额或配额不足、限流及服务器网络异常；脚本的格式校验不验证这些条件。
6. **旧会话沿用旧模型**：改变默认模型后，新建对话再试；已有会话保留创建时的模型选择。

不要把包含密钥、token 或完整业务数据的日志公开。排错可以提供脱敏错误、模型与提供方标识、失败时间及相关版本。

## root 执行脚本后，容器会不会读不到密钥？

Compose 部署脚本确认活动容器与 home 后，使用 `docker exec` 以容器配置用户运行官方写入逻辑，凭据文件权限为 `0600`。独立进程部署要求以 home 和凭据文件的所有者运行，拒绝以其他用户替换文件。已有错误属主应按实际运行用户单独修正，不能递归改变整个数据目录权限。

## 健康接口都是 200，是否代表模型能回答？

不代表。探针检查宿主、安装状态及插件就绪，不执行付费模型调用。仍需在应用中新建对话，验证真实回答、流式输出与历史恢复。页面能打开并不表示模型提供方可用。

## 更新或者更换密钥会清空账号和对话吗？

网页和脚本只更新官方存储中的默认 DeepSeek 凭据，保留其他凭据、账号和对话；更换密钥无需重启，不中断已开始的回答。正常服务更新仍须沿用已有站点数据。保留 `.local/data`、`.local/artifacts` 和备份，不要删除 `.local` 来绕过错误，也不要对正式环境重新执行空数据初始化。

## 普通用户登录成功却不能进入应用怎么办？

由管理员检查该账号的应用授权，以及目标插件是否启用。授予应用访问权不等于授予全部业务数据权限；业务数据范围仍由应用检查。不要用官方控制台 token 替代应用授权。
