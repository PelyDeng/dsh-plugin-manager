# DSH Plugin Manager v0.19.1

本版修复**精简部署包（archives 入口）无法独立部署**的问题，并让重复插件 id 在停旧之前给出可操作的失败信息。宿主仍是 `0.1.6-alpha.1`（提交 `0a15e36e7f82b6ed45af6fa9759f29b40dcd965d`），manager、kit、auth、example 统一为 `0.19.1`。

## 修复：部署包现在真的能部署

- `release-site` 的构建 worker 过去固定用 `<站点根>/deploy/scripts/build.mjs`。那个文件只存在于源码检出里，而且固定跑 source 流程；发行包把它放在 `source/` 下，于是按包内 README 执行 `bash build.sh` 会立刻 `Cannot find module .../deploy/scripts/build.mjs`。0.18.0 起的精简部署包都有这个问题，只是发布工作流只打包、不部署，所以一直没被发现。
- 现在 archives 入口改用**随包管理器自己的 CLI** 拉起 worker（内部动作 `archives-worker`），站点根不再需要任何源码文件；source 入口照旧用检出里的 worker，两种入口不混用。
- Release 工作流新增 `deployment-smoke` 作业：用刚打出来的部署 ZIP 在一次性目录里真的跑一次 build，核对发布记录、逐步计时记录与 `/auth/health`、`/example/ready` 探针；发布必须等它通过。这条作业同时充当该入口的回归门禁。

## 变更：部署包不再附带 `optional/auth`

- 内置 auth、example 由站点构建从随包公开源码材料产出，已经在候选里。包里再带一份同 id 的 `optional/auth` 只会误导人把它放进 `incoming`，进而撞上 id 重复。
- 因此精简部署包不再生成 `optional/`，`package-deployment.mjs` 也去掉了只为它存在的 `--auth-manifest` 参数；`public-apps` ZIP 仍在发布附件里，供独立 CLI 与显式清单流程使用。
- 内置与 `incoming` 里出现同一个插件 id 时，现在在**准备部署输入**阶段就报错，并指明是哪个内置插件与哪个发布目录冲突（发生在停旧之前，不会影响正在运行的服务）。

## 安装与升级

本次附件包含 manager、kit、公共 auth/example 应用包、精简部署包、独立起步包和 SHA256SUMS.txt。核对摘要后按[首次部署指南](https://github.com/PelyDeng/dsh-plugin-manager/blob/v0.19.1/doc/first-deployment.md)操作。

- 源码站点：普通 `build.sh` / `build.ps1` 从当前现场收敛即可，本版不改数据与配置。
- 固定镜像站点：镜像无需更换，本版只改部署包与脚本行为。
- 已经用旧部署包部署过的站点：把新部署包解压覆盖公开脚本、`tools/`、`source/`、`framework-runtime.json` 与公开模板（`incoming/`、`.local/` 原样保留），再跑一次普通 build 即完成设备侧修正。
