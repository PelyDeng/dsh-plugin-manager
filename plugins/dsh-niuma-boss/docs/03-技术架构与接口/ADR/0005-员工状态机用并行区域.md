# 员工状态机用并行区域，不用一张平铺表

**状态**：已采纳（用户授权自行判断）

需求文档给的是一张平铺清单：`Idle、Patrol、GoTo、Work、Report、Return`。我们没照抄，
而是把员工拆成两个并行区域：**位置**（在哪、在不在走）和**子任务**（手上有没有活、活到哪一步）。

原因是这张平铺表必然产生非法态。后端不等前端走路——真实执行完全可能在员工还没走到会合点的
时候就开始了，甚至已经结束了。平铺成一张表就会出现「状态是 GoTo，同时又该是 Work」这种表达不了
的情况，只能靠布尔标志打补丁，而补丁正是状态死锁和表现错乱的来源。拆成两个区域之后，
「人在 moving、活已经 running」是合法且明确的。

**代价**：状态机的读法比一张表复杂一点，需要理解"每个区域各自只有一个状态是活的"。
区域内互斥让表现状态清楚，但不能单独保证派单归属。**员工同一时刻最多持有一个子任务**仍须由后端按 `task_protocol.yaml#claim` 校验并锁定，不能只看前端处于哪个状态。

**牛马大总管也使用并行区域**。按已确认的自主活动决定，`locomotion` 管位置、`duty` 管协作；空闲时可走动，有活回工位。回位动画不阻塞理解、派单和结果展示。这里同步现有 `agent_fsm.yaml`，不改变员工并行区域的决定。
