# 补充处理与后端编排的最小实现方案

2026-09-13 确认的方向：**目标识别、依赖调度、结果适用性、替代、重试与最终结果聚合，都由两个入口共享的管家后端负责**。游戏负责提交意图与展示权威结果，群聊具备同样的操作能力。

本文给出两件事的最小实现、涉及范围与分批计划，供确认后再动手：

1. `POST /supplement`：修改或追加当前任务目标的独立入口；
2. 支撑它的后端编排能力（输入版本、目标标识、替代、依赖、聚合）。

**本文描述的已全部实现**（分四批落地，见第五节；契约与接口现状见[管家任务订阅接口契约 v1](20260913-130116-管家任务订阅接口契约-v1.md)）。首轮验收提出的并发缺口与依赖语义重写记在契约第九节，本文第四节的「最小实现」描述以那份契约为准。

---

## 一、职责边界

先说清楚谁做什么，因为这决定后面每一项落在哪一侧。

| 能力 | 归属 | 说明 |
| --- | --- | --- |
| 听懂老板要什么 | **后端** | 包括判断一句补充是「换个说法」还是「改了范围」 |
| 把目标拆成可派出去的活 | **后端** | 拆几份、派给谁、按什么顺序，都由它决定 |
| 记录权威状态与结果 | **后端** | 任务、子任务、材料、终态 |
| 判断旧结果还适不适用 | **后端** | 补充进来之后，哪些结果能接着用、哪些要重做 |
| 重试与替代 | **后端** | 谁替代谁、旧尝试怎么终结、上游变了下游怎么办 |
| 给出本轮最终结论 | **后端** | 包含「部分完成」这种结论 —— 不让两个界面各自聚合 |
| 提交意图 | 入口 | 游戏与群聊都只是把老板的话按契约送进去 |
| 展示权威结果 | 入口 | 地图、人物、动画、页面布局；不推进业务终态 |
| 提交补充 | 入口 | 走 `/supplement`，与「新回合」「回答成员」分开 |

判据很简单：**同一件事在两个入口上必须得到同一个结论**。凡是「换个入口就会有不同答案」的判断，都必须在后端。

## 二、`POST /supplement`

### 请求

```http
POST {prefix}/supplement
{
  "taskId": "butler-task-…",
  "text": "标题再短一点，其余照旧",
  "requestId": "req-abc",        // 可选，幂等；规则与 /chat 相同
  "expectVersion": 2             // 可选，并发依据
}
→ 200 text/event-stream（事件与 /chat 同形）
```

三个入口各管一件事，不能混用：

| 入口 | 什么时候用 | 不做什么 |
| --- | --- | --- |
| `POST /chat` | 开一个**新的**管家回合 | 不修改已经存在的任务 |
| `POST /reply` | 回答指定成员提出的问题 | 不改目标 |
| `POST /supplement` | 修改或追加**当前**任务的目标 | 不新建任务 |

`/supplement` 必须绑定 `taskId`：没有它就只能靠「当前会话最近一轮」猜，而补话与补目标混在一起正是要避免的。

### 语义（四条来自确认意见）

1. **只改表达** —— 范围与目标没变，管家复用仍然适用的结果，按新表达重新汇总。
2. **改范围或追加工作** —— 管家判断需要追加哪些执行、替代哪些旧的；旧终态不改写。
3. **接受不等于处理完成** —— 接口返回的是「已接受」，随后的事件流说明处理到哪了；最终汇总必须处理完**最新已接受**的输入。
4. **任务已终结时明确拒绝** —— 返回 `409`，`code: task_already_finished`，消息里说明「这是新一轮，请用 /chat 提交」。**不自动创建新任务**：那是老板的决定，不是接口替他做的。前端保留草稿，让老板决定是改到新任务上还是留着。

### 版本与并发

`expectVersion` 是乐观并发的依据：客户端提交时带上它看到的版本，服务端对不上就返回 `409`，`code: version_conflict`，并在响应里给出当前版本。

不传 `expectVersion` 时不检查 —— 但服务端仍然串行接受，不会出现两次补充互相覆盖。

### 与现有接口的一致性

错误码、幂等、事件流形态、鉴权与归属校验全部沿用现有约定，不新造一套：

- 同一个 `requestId` 重复提交 → 拿回首次的凭据，不重放第二次补充；
- `taskId` 不属于当前登录或不属于该会话 → `404 task_not_found`；
- 任务正在跑 → 不拒绝（补充本来就是运行中提出来的），但要等当前执行到安全点。

## 三、后端编排的最小实现

### 输入版本

| 字段 | 位置 | 含义 |
| --- | --- | --- |
| `acceptedVersion` | 任务 | 已接受的输入版本，从 1 开始；每接受一条补充原子 +1 |
| `processedVersion` | 任务 | 管家已经处理到的版本 |

规则：

- 接受补充时 `acceptedVersion += 1`，**原文一并保留**（`task_inputs` 表）；
- 管家处理完一批工作、核对过结果适用性之后才把 `processedVersion` 追平；
- **汇总前必须 `acceptedVersion === processedVersion`**，否则汇总作废重算 —— 这是「接受不等于处理完成」的落点；
- 任务终结后不接受新补充（见上面的第四条语义）。

### 目标标识与替代（第二字段群）

| 字段 | 位置 | 含义 |
| --- | --- | --- |
| `logicalId` | 子任务 | 同一个目标跨重试/替代保持不变 |
| `supersedes` | 子任务 | 替代了哪一条子任务；旧记录保留、状态终结 |

最小规则：

- 新目标用新的 `logicalId`；同一目标的重做沿用旧的，并指向被替代的那条；
- 聚合只看「当前有效的那一条尝试」（`supersedes` 链的末端），历史失败保留但不拉低结论；
- 换人执行也要另建子任务，不改写旧的 —— 与现有「`dispatched` 时锁定归属」一致。

### 依赖（第三字段群）

`dependsOn` 记到子任务上，只引用同一个任务内的 `logicalId`。最小规则：

- 依赖没终结时下游留在 `queued`，**不占员工**；
- 上游取消或失败时下游按失败收尾，并在 `error` 里说明「前提没有满足」，不伪造员工报错；
- 现在管家是**串行**调度（一份一份派），加 `dependsOn` 不改变这一点；并行是单独一批。

### 聚合与「部分完成」（第四字段群）

现在部分失败落在 `completed`、失败数写在 `error` 里。要引入任务级 `partial`：

- 由后端按当前有效尝试统一计算，两个入口读同一个结论；
- 判定依据：有没有可用成果、有没有外部待办、有没有未完成的目标；
- 与 `external_pending` 的先后：有外部待办且无未完成目标 → `external_pending`；还有目标没结论 → `partial`。

## 四、涉及范围

### 数据

索引升到 **v4**（迁移方式与 v2→v3 相同：在事务里增列增表，版本号最后写）：

| 表 | 变更 |
| --- | --- |
| `tasks` | 加 `accepted_version`、`processed_version` |
| `subtasks` | 加 `logical_id`、`supersedes`、`depends_on` |
| `task_inputs`（新） | 一条补充一行：任务、版本、正文、接受时间、来源（chat/supplement） |

回滚约束照旧：旧代码读到新版本会拒绝启动，降版本要先降库。

### 代码

| 文件 | 变更 |
| --- | --- |
| `src/store.ts` | 新表与新列、输入版本的原子递增、有效尝试的查询 |
| `src/butler.ts` | `submitSupplement()`；理解轮支持「补充」意图；汇总前核对版本；聚合改成按 `logicalId` 选有效尝试 |
| `src/task-model.ts` | 任务态加 `partial`；子任务态不变 |
| `src/web.ts` | 新增 `/supplement` 路由；`/task` 快照带上版本与 `logicalId` |
| `src/protocol.ts` | 派活请求带 `logicalId`（让员工在自己的记录里能串起来） |

### 对外契约

`/task` 快照要能读出 `acceptedVersion`、`processedVersion` 与每条子任务的 `logicalId`／`supersedes`；`/events` 增加 `input.accepted` 事件（补充被接受）与 `task.partial` 结论。

## 五、分批计划

每批独立可交付、可验收，做完再定下一批。

### 第 1 批：补充入口与输入版本（最小可用）—— **已完成**

已落地（提交 `780245f`）：`POST /supplement`、`acceptedVersion`/`processedVersion`、`task_inputs` 表；理解轮判断补充性质；任务终结时拒绝；幂等与并发依据接入现有机制。

实现与本文的差异，两处：

- **运行中补充**不是排队，而是「等当前这一轮跑到安全点」再处理（轮询等待，可被取消）。不打断正在跑的活这一点做到了，但等待期间不占用任何队列位置。
- **只改表达**的处理是：大总管的结论作为 `chat` 事件给出、版本追平，随后照常走 `closeTask`。也就是说它不会强行把任务收成 `completed` —— 还有成员在等回话时任务仍然停在 `waiting_user`，这与现有语义一致。

验证：9 项测试，覆盖版本递增与原文落库、只改表达不重复派活、改范围追加到同一轮（编号接着排）、终结拒绝且不开新任务、版本冲突、跨用户、幂等、不打断正在跑的一轮、以及 `input` 事件先于处理结果。

**这一批不做**：替代旧尝试、依赖、`partial`。限制见契约文档第五节。

- `POST /supplement`、`acceptedVersion`/`processedVersion`、`task_inputs` 表；
- 理解轮判断补充性质：只改表达就复用结果重新汇总；改了范围就按现有能力重新派活（此时还不替代旧尝试，只追加）；
- 任务终结时拒绝，`task_already_finished`；
- 幂等与并发依据接入现有机制。

**验收**：任务跑到一半提补充，两边入口都看到版本递增；汇总内容反映最新补充；改表达时不会重复派活；任务已终结时补充被拒且没有新任务被创建。

**这一批不做**：替代旧尝试、依赖、`partial`。限制要写进契约文档，不能默默不提。

### 第 2 批：目标标识与替代 —— **已完成**

已落地（提交 `f732c57`）：子任务带 `logicalId`（目标标识）与 `supersedes`（替代了哪条尝试）；聚合只看每个目标当前有效的尝试；四类非法声明在派活那一刻被拒。索引 v5。

与本文的差异：**自动重试**（超时或入口不可用之后由后端自己重做）没做 —— 替代的**表达与聚合**已经通了，但谁来发起重做目前只有「补充轮里大总管声明」这一条路径。

- `logicalId`／`supersedes`；同一目标的重做沿用标识并指向被替代的那条；
- 聚合只看有效尝试；历史失败保留。

**验收**：同一目标重做两次之后，结论不会被第一次的失败拉低，历史里两条都看得到。

### 第 3 批：依赖 —— **已完成**

已落地（提交 `5513200`）：`dependsOn` 记到子任务上，只有前置**成功**才派；前置失败、取消、等人回话、带外部待办都不派，如实记「前置没有完成，这一步不派了：g1（failed）」。引用只允许指向已有目标或本次计划中更早的目标，因此天然无环。索引 v6。

与本文的差异：上游 `external_pending` 时下游一律不派 —— 游戏侧 `ready_rules` 里「材料就绪且不需要外部操作则照常派」那个分支没做，因为员工侧还没声明「这件事需不需要外部操作」。

- `dependsOn`、上游失败对下游的传导、等待时不占员工。

**验收**：两步依赖的任务里，第一步失败时第二步不派出去，且说明原因。

### 第 4 批：聚合结论与 `partial` —— **已完成**

已落地（提交 `799e580`）：一部分成、一部分败时任务态是 `partial`，由后端按当前有效尝试算出；全败仍 `failed`、全成仍 `completed`、有人等着时不收尾。指标卡与历史筛选都认这个状态。

- 任务级 `partial`；汇总口径统一由后端给出。

**验收**：一个子任务成功、一个失败时，两边入口都显示「部分完成」而不是「完成」。

## 六、没实现之前怎么如实表达

在补齐之前，契约文档把这些列为**待完成**并写清限制，而不是让任一界面顶上：

| 现在能做到 | 现在做不到 | 限制怎么写 |
| --- | --- | --- |
| 新回合（`/chat`）、回答成员（`/reply`） | 修改当前目标 | 契约文档写明「`/supplement` 待实现；现在只能用 `/chat` 开新回合，旧任务不会被修改」 |
| 单层计划、串行调度 | 依赖、并行、替代 | 写明「重试会新建子任务，但不认『同一目标』；结论按全部子任务算，可能被已经替代掉的失败拉低」 |
| `completed` / `failed` | `partial` | 写明「部分失败落在 `completed`，失败数在 `error` 里；两边读同一个值，不要自行聚合出第三种结论」 |

这三条限制都要进契约文档第五节，随批次推进逐条删掉。

## 七、与游戏侧 `task_protocol.yaml` 的对照

游戏侧那份契约比管家现在的实现完整。补齐的方向是把它逐条搬到后端，而不是让游戏侧降级适配：

| 游戏侧机制 | 管家现状 | 落在哪一批 |
| --- | --- | --- |
| `acceptedVersion` / `processedVersion` | 无 | 第 1 批 |
| `logicalId` / `supersedes` | 无 | 第 2 批 |
| `dependsOn` | 无 | 第 3 批 |
| `retryOf` | 无（重试靠重新派活） | 第 2 批 |
| `unmetGoals` | 无 | 第 4 批 |
| `partial` | 无（落在 `completed`） | 第 4 批 |
| `external_pending` | **已实现** | — |
| `requestId` 幂等（含跨重启） | **已实现** | — |
| 事件序号与续传 | **已实现** | — |
| 归属与鉴权 | **已实现** | — |

字段名可以按管家的规范调整（例如 `logicalId` 叫别的），但**语义要能一一对上**，转换规则写进契约文档。
